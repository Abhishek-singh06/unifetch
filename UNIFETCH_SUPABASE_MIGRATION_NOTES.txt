UNIFETCH V2 SUPABASE MIGRATION NOTES & AUDIT REPORT

1. ROOT CAUSE OF "ERROR: 42P13: no language specified"
------------------------------------------------------------------------------
During the addition of DROP FUNCTION statements, an accidental duplicate line was
introduced immediately preceding confirm_outside_payment_received:
  CREATE OR REPLACE FUNCTION public.confirm_outside_payment_received(uuid);
This statement had no argument names, no return type, no LANGUAGE specification, and no body.
When the Supabase SQL Editor evaluated this statement, PostgreSQL halted with:
  ERROR: 42P13: no language specified

Fix applied:
- The rogue duplicate statement was completely removed.
- All 31 functions in UNIFETCH_SUPABASE_FINAL_MIGRATION.sql.txt were audited.
- Every function now explicitly declares:
    LANGUAGE plpgsql
    SECURITY DEFINER (where appropriate)
    SET search_path = public
  and ends cleanly with:
    $$;


2. ROOT CAUSE OF "ERROR: 42601: operator too long at or near '================'"
------------------------------------------------------------------------------
In PostgreSQL, raw sequences of '=' or '-' characters without the leading '-- ' comment
prefix are parsed as user-defined operator symbols. When a line like
==============================================================================
is evaluated by PostgreSQL, it fails with:
  ERROR: 42601: operator too long at or near "================"

Fix applied:
- All raw '===' and '---' decorative separator lines have been eliminated from both
  UNIFETCH_SUPABASE_FINAL_MIGRATION.sql.txt and UNIFETCH_SUPABASE_VERIFICATION.sql.txt.
- Every section heading is now a clean, single-line SQL comment beginning strictly with '-- '.
- Zero un-commented plain text exists in either executable SQL file.


3. CONFIRMATION OF PREVIOUS FIXES
------------------------------------------------------------------------------
A. buy_credits Return Type Conflict (ERROR 42P13):
   - PostgreSQL prohibits CREATE OR REPLACE FUNCTION from altering return types (e.g. from
     legacy BOOLEAN / VOID to V2 UUID).
   - Resolved with explicit DROP FUNCTION IF EXISTS public.buy_credits(integer, text, text);
     and argument variations before defining the V2 UUID-returning function.

B. outside_trips.traveler_id Does Not Exist (ERROR 42703):
   - The canonical column in supabase_schema.sql and the V2 frontend (app/outside/browse/page.tsx
     and app/outside/trips/create/page.tsx) is `creator_id`.
   - All references to traveler_id have been eliminated.
   - ALTER TABLE public.outside_trips ADD COLUMN IF NOT EXISTS creator_id UUID ... was added
     to guarantee existing tables have the column before RLS policies run.

C. Schema Alignment for Outside Tasks & Messages:
   - outside_messages uses canonical `is_system BOOLEAN NOT NULL DEFAULT FALSE` matching
     app/outside/[id]/page.tsx.
   - outside_requests has all columns safely ensured via ALTER TABLE ... ADD COLUMN IF NOT EXISTS
     (including trip_id, final_reward, payment_status, contact_shared, etc.).
